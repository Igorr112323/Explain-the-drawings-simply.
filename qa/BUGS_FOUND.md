# Баги, найденные на QA-прогоне

Корпус: `scripts/qa/generate_corpus.py` (режим `Principal QA / Chaos Engineer`), прогон
`scripts/qa/run_qa.py` → реальные `vision-api` → `ikguide-builder` → `gost-translator` → `schema` →
`pdf-exporter` → проверка PDF через PyMuPDF. Никаких моков в продуктовой цепочке: мокается только
браузерный canvas при сборке кропов (в Node нет `canvas`; см. P3-3).

Приоритеты: **P0** — сервис падает / данные теряются, **P1** — неверная инструкция в цех,
**P2** — заметная ошибка или риск, **P3** — мелочь/UX.

## P0-1. Сервис распознавания умирает от OOM на потоке крупных сканов

**Как воспроизвести**

```bash
services/vision-api/.venv/bin/python scripts/qa/generate_corpus.py --out /tmp/corpus_small --count 40 --fuzz 12
services/vision-api/.venv/bin/python scripts/qa/run_qa.py --corpus /tmp/corpus_small --out /tmp/qa_out
```

На 41-м кейсе (`fuzz_zero_bytes.png`) `POST /v1/recognize` получает `Connection refused`, все
последующие кейсы — `status=0`. `dmesg`:

```
oom-kill:constraint=CONSTRAINT_NONE ... task_memcg=/user, task=python
Out of memory: Killed process 58738 (python) total-vm:4991276kB, anon-rss:3408092kB
```

**Причина.** `PageStore` держал до 32 полных страниц 30 минут: `MAX_STORED_PAGES = 32`,
`PAGE_TTL_SECONDS = 30 * 60`. На каждый лист — распознанное изображение до 2600 px по длинной
стороне (≈13–20 МБ BGR), плюс текст. Лимит «по штукам» ничего не говорит о памяти, поэтому после
40 крупных сканов RSS дошёл до 3,4 ГБ и ядро убило процесс вместе с uvicorn.

**Исправление**

- `services/vision-api/app/config.py`: бюджет по памяти вместо счётчика страниц —
  `MAX_STORED_BYTES = 320 * 1024 * 1024`, `MAX_STORED_PAGES = 8`, `PAGE_TTL_SECONDS = 10 * 60`,
  `MAX_WORKING_SIDE` 2600 → 2200, новый `OCR_MAX_SIDE = 1600`, `MEMORY_SOFT_LIMIT_BYTES = 1400 МБ`.
- `services/vision-api/app/pages.py`: `PageStore` считает `page_bytes()` (изображение + строки
  векторного слоя) и вытесняет самые старые страницы, пока не влезет в бюджет.
- `services/vision-api/app/main.py`: аварийный клапан `_guard_memory()` — если RSS перевалил за
  мягкий лимит, кэш очищается, а в ответ добавляется честное предупреждение.
- `services/vision-api/app/ocr.py`: OCR получает картинку не шире 1600 px по длинной стороне
  (меньше арены onnxruntime — меньше пик).

**Регрессия.** `services/vision-api/tests/test_robustness.py::test_page_store_keeps_memory_budget_not_item_count`,
`::test_page_store_evicts_oldest_first`, `::test_memory_soft_limit_is_lower_than_typical_crash_point`.

**Проверка после фикса.** Прогон 1 060 файлов: `serverDeaths: 0`, RSS держится в пределах
≈700–950 МБ (см. `qa/QA_REPORT_1000.md`).

## P0-2. Картинка 1200×1 (полоска) кладёт весь движок: SIGSEGV в нативном OCR

**Как воспроизвести**

```bash
curl -sS -X POST -F "files=@fuzz_line_1200x1.png" http://127.0.0.1:8000/v1/recognize
curl -sS http://127.0.0.1:8000/health   # → curl: (7) Failed to connect
```

Первый запрос обрывает соединение (`status=0`), второй — сервиса уже нет. В логах uvicorn пусто:
это не исключение Python, а аварийное завершение нативного кода.

**Причина.** Детектор `rapidocr_onnxruntime` на вырожденном изображении (высота 1 px) падает
внутри C++ (onnxruntime/OpenCV), а SIGSEGV перехватить нельзя — умирает весь процесс, то есть у
пользователя пропадает распознавание до перезапуска приложения.

**Исправление**

- `services/vision-api/app/preprocessing.py`: `reject_degenerate()` — лист с меньшей стороной
  < 48 px или соотношением сторон > 40 отклоняется до OCR с понятным текстом
  («Изображение слишком маленькое (1200×1 px): загрузите лист чертежа целиком»), API отвечает 422.
- `services/vision-api/app/ocr.py`: `RapidOcrEngine._prepare()` возвращает `None` для вырожденных
  картинок — нативный движок в этом случае вообще не вызывается (второй рубеж защиты).

**Регрессия.** `tests/test_robustness.py::test_ocr_rejects_degenerate_images_without_touching_native_code`,
`::test_degenerate_sheet_is_reported_not_crashed`, `::test_strip_upload_returns_422_and_keeps_service_alive`,
`::test_pages_from_upload_refuses_degenerate_file`.

## P1-1. ГОСТ-переводчик выдавал физически невозможный инструмент: сверло Ø−1,3 мм

Найдено фаззингом 2 600 строк (`scripts/qa/fuzz_gost.ts`): 245 провалов, из них реальные —

| Обозначение | Что было | Что должно быть |
|---|---|---|
| `М0×1,25-6H` | резьба Ø0, `tapDrillMm = −1,3` | неразборчиво (`unknown`) |
| `М1×1,25-6H` | шаг больше диаметра, сверло Ø−0,3 | `unknown` |
| `М20×29-6H` | шаг 29 мм, сверло Ø−9 | `unknown` |
| `М920×2-6H` | резьба Ø920 мм | `unknown` (ГОСТ 24705 держит М1…М600) |

Рабочему ушло бы «Сверло Ø−1,3 мм» в таблице инструмента — и это не гипотетика: OCR регулярно
путает `0`/`О` и теряет знаки, поэтому такие строки реально приходят с листа.

**Исправление.** `packages/gost-translator/src/parsers/thread.ts`: проверки
`1 ≤ d ≤ 600`, `0 < P ≤ 6,5`, `P < d` — при нарушении `parseThread` возвращает `null`, и
обозначение честно попадает в «не распознано» (`unknown`), а не в инструмент.

**Регрессия.** `packages/gost-translator/src/parsers/thread.test.ts`:
`rejects threads that cannot exist and never emits a negative tap drill`,
`keeps the tap drill strictly inside the thread diameter`.

**Проверка после фикса.** Фаззинг: `2600 строк, провалов 0`.

## P2-1. `ikguide-vision.exe` оставался висеть после падения приложения (зомби + занятый порт)

Приложение останавливало движок только по `RunEvent::Exit`. Если его снимали через диспетчер
задач, движок продолжал держать порт 8000, а следующий запуск считал «движок уже запущен» и не
управлял им: «закрыл приложение — процесс остался».

**Исправление**

- `apps/desktop-tauri/src-tauri/src/lib.rs`: при запуске движку передаётся `--parent-pid <PID>`.
- `services/vision-api/engine_entry.py`: сторож `watch_parent()` — каждые 5 с проверяет родителя
  (`OpenProcess`+`WaitForSingleObject` на Windows, `os.kill(pid, 0)` иначе) и завершает процесс,
  если приложения больше нет.
- `scripts/check-native-configs.mjs`: три новые проверки, чтобы связка не разъехалась (всего 152).

**Регрессия.** `services/vision-api/tests/test_parent_watchdog.py` (5 тестов).

## P2-2. Любой сервис с кодом 200 на 127.0.0.1:8000 считался «движком на связи»

`health_ok()` в `lib.rs` и `pingHealth()` в веб-клиенте проверяли только `HTTP 200`. У инженера на
8000 легко оказывается Jupyter/отладочный сервер: меню писало «на связи», а распознавание не
работало; `lib.rs` при этом вообще не поднимал движок.

**Исправление.** Оба места требуют, чтобы `/health` вернул `service: "ikguide-vision-api"`;
`lib.rs` дочитывает ответ до конца (заголовки и тело приходят разными пакетами), ограничение 8 КБ.

**Регрессия.** `apps/studio-web/src/lib/engine.test.ts::чужой сервис на 8000 не считается движком`,
проверки `check:native` в `scripts/check-native-configs.mjs`.

## P2-3. QA-обвязка врала дважды: PDF без кропов и «фото», на котором ничего не видно

Найдено при разборе собственного прогона (это баги тестового контура, но они искажали выводы).

1. **PDF собирался без фрагментов чертежа.** QA-скрипт вызывал `buildIllustrations(doc)` без
   `fragments`, поэтому каждая страница шага получала заглушку «Схема доступна только в браузере»,
   а `withImages` = 0. Настоящий `pipeline.ts` режет лист через canvas. В Node canvas нет, поэтому
   `scripts/qa/build_docs.ts` теперь воспроизводит ту же геометрию (`cropPercent` → `cropBitmap`,
   `stepFragment` → `fragmentBox`) на `pngjs` и отдаёт PNG-фрагменты штатной
   `buildIllustrations(doc, { steps, cover })`. После фикса: 47/47 PDF с настоящими кропами,
   `drawn ≥ 1` на каждой странице с иллюстрацией.
2. **«Фото с телефона» было нечитаемым.** Генератор накладывал `GaussianBlur(σ=6)` на каждое
   пятно (1–3 прохода): штрихи превращались в кашу (`sharpness ≈ 1`), и любой вывод про OCR на
   фото был нечестным. Теперь σ ≤ 0,6, пятна полупрозрачные, JPEG 60–90. На новых фото OCR читает
   `Ø20 H7`, `M8-7H`, `Ra 1,6` — как на реальном снимке.

3. **Проверка PDF давала ложные срабатывания.** Наложения считались по «блокам» PyMuPDF (абзац
   накрывает соседние абзацы) — теперь по строкам; картинки считались по странице, а jsPDF держит
   общий словарь ресурсов (9 «картинок» на каждой странице) — теперь по уникальным xref плюс
   `page.get_image_info()` для факта отрисовки.

## P3-1. Два шага могут получить одинаковый фрагмент листа

Шаг «Подготовка заготовки» и «Финальный контроль» не имеют своих обозначений, поэтому
`cropForEntries` берёт объединение видов (`views`), и в 14 из 55 документов оба шага показывают
один и тот же кроп. Иллюстрация не врёт (это действительно вид листа), но две одинаковые картинки
на 9 страницах выглядят как недоработка. Не правилось: изменение логики выбора кропа меняет
вёрстку инструкции, а дизайн по условию задачи не трогаем.

## P3-2. `cropUniqueShare` 68,6 % — часть повторов идёт от строк спецификации

Строки таблицы позиций идут с одинаковой шириной (`w = 51,01 %`), различаясь только `y`. Это
корректно, но означает, что «уникальность кропа» нельзя мерить только числом уникальных рамок.

## P3-3. Кириллица в OCR — ограничение модели, а не кода

`rapidocr_onnxruntime` в этой сборке знает латиницу/китайский: `ПОЗИЦИЯ` распознаётся как
`MO3NLNA`, `Сталь 45` — как `CTab45`. Размеры и резьбы при этом читаются (`Ø20 H7` → `020 H7`,
`M8-7H` → `M8-7H`), поэтому инструкция собирается, но русские подписи в тексте листа — нет.
Лечится русской rec-моделью: движок уже принимает `IKGUIDE_OCR_REC_MODEL` и `IKGUIDE_OCR_REC_KEYS`,
нужны только сами веса (в песочнице их не скачать — доступны лишь PyPI/GitHub API).

## Что НЕ подтвердилось (чтобы не чинили зря)

- `blankRodMm = 11,7` для `М12-6g` — не баг: пруток под плашку намеренно меньше номинала.
- Отсутствие шагов на белом/чёрном листе, на `<script>alert(1)</script>` и обрезанных PDF — не
  заглушка: распознавать нечего, инструкция честно собирается из двух шагов и предупреждений.
- «Квадратики» вместо `Ø ± ° × № ≈` в PDF не появляются: проверка `pdf_bad_encoding` — 0 на всём
  корпусе (шрифт DejaVu вшит в экспортёр).
